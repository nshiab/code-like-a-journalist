# Publishing a TypeScript library

Do you have bits of code that you keep copying and pasting from one project to another? If so, it probably means you should create a library!

In this lesson, I'll show you how to create an open-source library with Node.js and publish it on [npm](https://www.npmjs.com/). We'll write TypeScript, test it, and compile it into JavaScript with type declarations so other projects can use it.

I'm assuming you've completed the previous lessons, especially these:

- [Using libraries](/pushing-further/libraries)
- [Understanding library versions](/ninja-moves/semver)
- [Using tests in your projects](/ninja-moves/tests)

## Creating an npm account and project

npm is the package registry where we will publish our library. Start by [creating an npm account](https://www.npmjs.com/signup). For the manual publishing workflow in this lesson, enable [two-factor authentication](https://docs.npmjs.com/configuring-two-factor-authentication) on your account.

Our package will be named `@your-username/my-first-library`. The part before the slash is called a **scope**. Replace `your-username` with your npm username throughout this lesson, and choose a package name that is available in your scope.

The project generator used elsewhere in the course prepares data analysis projects. Here, we will configure a small standalone library so we can control the files npm distributes. Create a new folder and open it in VS Code. Use the latest Node.js LTS, then initialize the project in its terminal:

```sh
npm init -y
npm install --save-dev typescript @types/node vitest
```

In `package.json`, set `"type": "module"` so our code uses ES modules. We'll finish the rest of this file shortly.

## Coding the library

It's time to write some code! We'll reuse the percentage function from the [tests lesson](/ninja-moves/tests), with rounding added.

Create a `functions` folder and a `getPercentage.ts` file with the code and documentation below. The comment above the function is **JSDoc**: editors can display it when someone uses the function.

````ts showLineNumbers filename="functions/getPercentage.ts"
/**
 * Calculates a percentage, rounds it, and adds a percentage sign ("%").
 *
 * @example
 * ```ts
 * getPercentage(50, 200); // "25%"
 * getPercentage(0, 0);   // "0%"
 * ```
 *
 * @param current - The value to calculate the percentage for.
 * @param total - The total value to calculate the percentage against.
 * @returns The rounded percentage, or "0%" if total is zero.
 */
export default function getPercentage(
  current: number,
  total: number,
): string {
  if (total === 0) {
    return "0%";
  } else {
    const percentage = Math.round((current / total) * 100);
    return `${percentage}%`;
  }
}
````

Create an `index.ts` file at the root of the project. This will be the entry point of your library. We import our function and re-export it with a name, so people can use `import { getPercentage } from "..."`.

If your library grows, you can gather its public functions and classes here.

```ts showLineNumbers filename="index.ts"
import getPercentage from "./functions/getPercentage.ts";

export { getPercentage };
```

Testing your code is critical before publishing it. Create a `tests` folder and add a `getPercentage.test.ts` file. We'll import from the entry point to test what the library exports.

```ts showLineNumbers filename="tests/getPercentage.test.ts"
import { test, expect } from "vitest";
import { getPercentage } from "../index.ts";

test("should return 50%", () => {
  expect(getPercentage(50, 100)).toBe("50%");
});
test("should round to 33%", () => {
  expect(getPercentage(33.333, 100)).toBe("33%");
});
test("should return 0% for a zero current value", () => {
  expect(getPercentage(0, 100)).toBe("0%");
});
test("should return 0% for a zero total", () => {
  expect(getPercentage(1, 0)).toBe("0%");
});
```

Run `npx vitest run tests/getPercentage.test.ts`. All four tests should pass! We use the same test syntax as in the generated projects.

## Configuring TypeScript

Node can run our TypeScript source directly, but it doesn't check the types and doesn't compile our library for distribution. We'll use the TypeScript compiler for those tasks.

Create `tsconfig.json` to check our library and its tests:

```json showLineNumbers filename="tsconfig.json"
{
  "compilerOptions": {
    "noEmit": true,
    "target": "esnext",
    "module": "nodenext",
    "rewriteRelativeImportExtensions": true,
    "erasableSyntaxOnly": true,
    "verbatimModuleSyntax": true,
    "strict": true,
    "types": ["node"]
  },
  "include": ["index.ts", "functions/**/*.ts", "tests/**/*.ts"]
}
```

Run `npx tsc --noEmit`. This checks our source and tests without creating output files.

Now create a second configuration for the build. It extends the first one, enables output, and limits compilation to the code we want to distribute:

```json showLineNumbers filename="tsconfig.build.json"
{
  "extends": "./tsconfig.json",
  "compilerOptions": {
    "noEmit": false,
    "noEmitOnError": true,
    "declaration": true,
    "rootDir": ".",
    "outDir": "./dist"
  },
  "include": ["index.ts", "functions/**/*.ts"],
  "exclude": ["tests", "dist", "node_modules"]
}
```

Run `npx tsc -p tsconfig.build.json`. You should see a new `dist` folder containing:

```text
dist/
  index.js
  index.d.ts
  functions/
    getPercentage.js
    getPercentage.d.ts
```

The `.js` files are the executable code. The `.d.ts` files describe its types for TypeScript users. The compiler preserves our JSDoc in the declarations, so readers still get help from their editor. See [TypeScript's guide to publishing declarations](https://www.typescriptlang.org/docs/handbook/declaration-files/publishing.html).

The [`rewriteRelativeImportExtensions` option](https://www.typescriptlang.org/tsconfig/rewriteRelativeImportExtensions.html) changes relative `.ts` imports into `.js` imports in the output. Open `dist/index.js` to see the difference!

We publish this compiled output because Node does not strip TypeScript types from packages inside `node_modules`. Our library can also be used by JavaScript projects without making them compile our source.

## Preparing the package

Update `package.json` with the fields below. **Keep the `devDependencies` section created by npm** in addition to these fields; its version numbers depend on when you installed TypeScript, `@types/node`, and Vitest.

```json showLineNumbers filename="package.json"
{
  "name": "@your-username/my-first-library",
  "version": "0.1.0",
  "description": "A small helper for rounded percentages",
  "type": "module",
  "license": "MIT",
  "files": ["dist"],
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js"
    }
  },
  "scripts": {
    "check": "tsc --noEmit",
    "test": "vitest run tests/getPercentage.test.ts",
    "build": "tsc -p tsconfig.build.json",
    "prepublishOnly": "npm run check && npm test && npm run build"
  }
}
```

Here's what these settings do:

- `name`, `version`, and `description` identify the library. See the [SemVer lesson](/ninja-moves/semver) for version numbers.
- `license` declares the license. Here we chose [MIT](https://opensource.org/license/mit); add its text in a `LICENSE` file, with your name and the year.
- `files` limits the published code to `dist`. npm also includes files such as `package.json`, `README.md`, and `LICENSE`.
- `exports` points imports to our compiled entry point and gives TypeScript the declarations. This example publishes an ES module.
- `scripts` gives us convenient commands and runs checks, tests, and the build automatically before `npm publish`. See the [npm lifecycle documentation](https://docs.npmjs.com/cli/v11/using-npm/scripts).

If `npm init` created a `"main": "index.js"` field, remove it: our entry point is described by `exports`. If you copied `"private": true` from an analysis project, remove it too when you intend to publish; that setting blocks publication.

Create `README.md` to explain the package and show how to use it. npm displays this file on the package page.

````md showLineNumbers filename="README.md"
# My first library

A helper created as part of the [Code Like a Journalist](https://www.code-like-a-journalist.com/en) course.

## Installation

```sh
npm install @your-username/my-first-library
```

## Usage

```ts
import { getPercentage } from "@your-username/my-first-library";

getPercentage(50, 200); // "25%"
getPercentage(0, 0);   // "0%"
```
````

npm displays the README, but doesn't generate a browsable API reference from JSDoc for us. For a larger library, you can build a separate documentation site.

I strongly encourage you to save the source and both npm configuration files in Git! See the [GitHub lesson](/git-and-github/github-basics). Add `node_modules/` and `dist/` to `.gitignore`: they can be recreated with `npm ci` and `npm run build`.

## Checking the package locally

Before uploading anything, run:

```sh
npm run check
npm test
npm run build
npm pack --dry-run
```

Inspect the file list. It should contain the JavaScript, declarations, package metadata, README, and license. The tests and TypeScript source don't need to be shipped in this example. See the [npm package contents documentation](https://docs.npmjs.com/cli/v11/commands/npm-publish#files-included-in-package).

To try the **actual package** locally, run `npm pack`. This creates an archive such as `your-username-my-first-library-0.1.0.tgz` without publishing it.

Create a separate project folder, initialize it with `npm init -y`, set `"type": "module"` in its `package.json`, and install that archive using its full path:

```sh
npm install /full/path/to/your-username-my-first-library-0.1.0.tgz
```

Create `main.ts` with this code:

```ts showLineNumbers filename="main.ts"
import { getPercentage } from "@your-username/my-first-library";

const percentage = getPercentage(20, 100);
console.log(percentage);
```

Run `node main.ts`. You should see `20%`! This checks that the compiled entry point works for a consumer, too. You can add the usual TypeScript project configuration here if you want to check the types.

## Publishing the library

Back in the library folder, run `npm login` and follow its browser sign-in flow. `npm whoami` lets you confirm which account you're using. See the [npm login documentation](https://docs.npmjs.com/cli/v11/commands/npm-login).

Preview the publication with `npm publish --dry-run --access public`. It runs the `prepublishOnly` checks but doesn't upload the package.

When you're ready to share it publicly, run:

```sh
npm publish --access public
```

Complete any authentication prompt. The `--access public` flag explicitly publishes our scoped package publicly. This manual workflow uses your account's two-factor authentication; the [npm publishing guide](https://docs.npmjs.com/creating-and-publishing-scoped-public-packages) explains the current requirements.

Once it succeeds, visit `https://www.npmjs.com/package/@your-username/my-first-library` with your actual username. Your code is available for others to install, and your README explains how to use it! 🤩

```sh
npm install @your-username/my-first-library@0.1.0
```

The import in `main.ts` stays the same. Keep this project: we'll use it again after publishing an update.

## Publishing a new version

Trust me: resist the urge to publish too quickly! A tiny change can break a library. Our `prepublishOnly` script helps by running checks and tests before each publication.

Let's make a small update. Add a sentence to your README explaining that percentages are rounded to the nearest whole number, then increase the version:

```sh
npm version patch --no-git-tag-version
```

This changes `0.1.0` to `0.1.1` in `package.json` and updates `package-lock.json`. Here, `--no-git-tag-version` lets us manage the Git commit and tag separately. You could use `minor` or `major` for larger changes, as explained in the [SemVer lesson](/ninja-moves/semver).

Run `npm publish --dry-run --access public` and inspect the result. When you're ready, run `npm publish --access public` again. npm runs our checks before uploading the new version! 🥳

A published name and version cannot be reused, so corrections need a new version number. Your package page should now show `0.1.1` and the updated README.

## Updating the consumer project

In the project that uses the library, run `npm outdated`. Look at `Current` (installed), `Wanted` (allowed by `package.json`), and `Latest` (marked `latest` on npm).

If `package.json` allows `^0.1.0`, `npm update @your-username/my-first-library` can install `0.1.1`. It updates the installed package and lockfile while keeping that range. To choose a version explicitly and update the dependency entry, run `npm install @your-username/my-first-library@0.1.1`.

Check that `node main.ts` still works. In a larger project, run your type checks and tests too. Of course, this particular update only changed documentation, but now you know the whole workflow. 🤓

## Automating publication

If you plan to update your library often, you can automate the checks and publication with GitHub Actions. One possible workflow is:

1. Create an issue for a bug or feature, then work on a branch.
2. Add tests for the change and open a pull request.
3. Run type checks, tests, and the build in GitHub Actions before merging.
4. Update the package version and save that change in Git.
5. Trigger a publishing workflow for a release or Git tag.

For the last step, look into [npm trusted publishing](https://docs.npmjs.com/trusted-publishers). It lets supported CI environments authenticate without storing a long-lived npm token. Configure it for your repository and workflow according to npm's documentation.

The [GitHub lesson](/git-and-github/github-basics) and [GitHub Actions lesson](/git-and-github/github-actions) will help you get there. Manual publishing is already a useful starting point!

## Private packages

Within a company, a private library can be useful for sharing tested code among teammates. npm also supports [private packages](https://docs.npmjs.com/creating-and-publishing-private-packages), with account and access requirements described in its documentation.

A public package is accessible to everyone. Choose the appropriate access setting for the code you intend to share.

We now have reusable code, tests, editor documentation, and a package that JavaScript and TypeScript projects can import. So stop copying and pasting the same helper between projects and give it a library of its own! 😎
