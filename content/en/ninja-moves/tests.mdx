# Using tests in your projects

Tests are widely used in programming to ensure that classes, functions, and methods behave as expected. When code is updated, tests guarantee that the changes are not breaking any of the work done previously.

But tests can also be very useful in data analysis and visualization projects. You can use them to make sure your calculations align with an independent reference. Or, once you have results, to ensure your code changes are not having unexpected impacts on your findings or visuals.

Personally, I use tests to increase my confidence in my work. I can double-check something once and write a test for it. Going forward, I’ll know for sure that this thing is guaranteed. And if the test fails, it means something very bad is happening and needs my attention!

In this lesson, we will code a simple function to calculate percentages and we will create tests to make sure it works as expected.

## Setup

Create a new folder, open it in VS Code, and use the latest Node.js LTS. In the terminal, run `npx @nshiab/setup-data-project` and choose no optional libraries. This creates the same project structure and tools as in the [setup lesson](/simple-data-analysis/setup).

We will write our script in `sda/main.ts`. Run `npm run sda` to execute it and rerun it automatically when you save changes. Run `npm run all-tests` to check formatting, lint rules, types, and tests; `npm run fix` can apply automatic formatting and lint fixes.

Use the `sda/helpers` folder (create it if needed) and put the `getPercentage.ts` file inside it with this code. It's the function we want to test. It expects two numbers and returns the percentage as a string.


```ts showLineNumbers filename="sda/helpers/getPercentage.ts"
export default function getPercentage(
    current: number,
    total: number,
): string {
    const percentage = (current / total) * 100;
    return `${percentage}%`;
}
```

Update `sda/main.ts` to use the function.

```ts showLineNumbers filename="sda/main.ts"
import getPercentage from "./helpers/getPercentage.ts";

console.log(getPercentage(50, 100));
```

The running `npm run sda` command executes the script when you save it.

Everything looks fine! The function returns `50%` as expected.

## Creating tests

Is our function really working as expected? Let's check!

Our generated project already includes [Vitest](https://vitest.dev/guide/) through Vite+. We will use `test` to describe each test and `expect(...).toBe(...)` to compare what our function returns with what we expect. There is nothing else to install!

Now, let's create the test file. One way to keep tests organized in a project is to keep the same file structure for the tests as for the rest of the code.

Here, we could create a folder `sda/tests` with a new file `getPercentage.test.ts` in it. Note that this file is a regular TypeScript file since it ends with `.ts`. The `.test` part lets Vitest recognize it as a test file.

Here's what the code below does:
- `test` creates a new test.
- The first parameter is a description of the test.
- The second parameter is a function. We run what we want in it (here `getPercentage`) and we check that the result is what we expect with `expect(...).toBe(...)`.
- If the result is what is expected, the test will pass. Otherwise, it will fail!

```ts showLineNumbers filename="sda/tests/getPercentage.test.ts"
import { test, expect } from "vitest";
import getPercentage from "../helpers/getPercentage.ts";

test("should return 50% for 50 out of 100", () => {
  const result = getPercentage(50, 100);
  expect(result).toBe("50%");
});
```

## Running tests

Run `npm run all-tests`. This checks formatting, lint rules, and TypeScript types, then runs the project's tests. If a formatting or lint check fails, run `npm run fix`, review the changes, and try again.

<OutdatedScreenshot src="/assets/ninja-moves/tests/run-tests.png" alt={"Running tests with Deno."} lang="en" />

While writing code, it's convenient to rerun a single test file automatically whenever it or its dependencies change. Use:

```sh
npx vp test sda/tests/getPercentage.test.ts --watch
```

Keep that command running for the rest of the lesson. Press `CTRL` + `C` to stop it. The watch command runs tests; `npm run all-tests` also runs the other project checks, so use it again before finishing your changes.

The [Vitest documentation](https://vitest.dev/guide/) explains more options.

## Adding tests

Depending on your context, the test we wrote just above might be sufficient. For example, maybe you just wanted to double-check the result of one step in your data analysis and you want it to stay this way going forward.

But for the sake of this lesson, let's add more tests here. Let's test edge cases.

For example, what is supposed to happen when the first number is `0`? And when the second is `0`? Maybe we want our function to return `0%` in both cases.

Update the file with the code below. When you save the modified file, the tests will be automatically rerun.

```ts showLineNumbers filename="sda/tests/getPercentage.test.ts" {9-17}
import { test, expect } from "vitest";
import getPercentage from "../helpers/getPercentage.ts";

test("should return 50% for 50 out of 100", () => {
  const result = getPercentage(50, 100);
  expect(result).toBe("50%");
});

test("should return 0% for 0 out of 100", () => {
  const result = getPercentage(0, 100);
  expect(result).toBe("0%");
});

test("should return 0% for 1 out of 0", () => {
  const result = getPercentage(1, 0);
  expect(result).toBe("0%");
});
```
<OutdatedScreenshot src="/assets/ninja-moves/tests/fail.png" alt={"A test failed."} lang="en" />

We can see that the second test passed but the third one failed!

When the `total` is `0`, our function is returning `Infinity%` instead of what we want, which is `0%`.

Let's update our `getPercentage.ts` to fix that. Update the file with the code below. When you save the file, the tests will rerun automatically.

```ts showLineNumbers filename="sda/helpers/getPercentage.ts" {5-7, 10}
export default function getPercentage(
  current: number,
  total: number,
): string {
  if (total === 0) {
    return "0%";
  } else {
    const percentage = (current / total) * 100;
    return `${percentage}%`;
  }
}
```

And now, we can see that the third test passed.

We also know that the previous behavior is still there because the first two tests passed too!

## Automated tests

You can always run tests locally, of course. You can even make a [task](/pushing-further/tasks) to make it easier to run them.

But if you are using GitHub, you can set up automated tests in your projects. This is a common setup for open-source libraries, but you can use it for anything you want.

For example, I have hundreds of tests in place for the [Simple Data Analysis library](https://github.com/nshiab/simple-data-analysis). You can [explore them here](https://github.com/nshiab/simple-data-analysis/tree/main/test/unit/methods).

I use GitHub Actions (check the [lesson about it](/git-and-github/github-actions)) to trigger them automatically when a pull request is opened or updated against the `main` branch.

The pull request shows whether the tests passed. If one or more fail, more work is needed before merging. Repository rules can also require these status checks to pass and block the merge button until they do. You can check the [workflow here](https://github.com/nshiab/simple-data-analysis/blob/main/.github/workflows/all-tests.yml).

It's just a few lines of code, but it guarantees that the library is working as expected. And it has saved me many times from publishing a new broken version of the library! 😇

## Testing dataviz

Tests are easy to set up when your code **returns** something like a string, number, date, array, or object.

But you can also use tests to compare web page elements, like charts, and more, with [Playwright](https://playwright.dev/). We used Playwright in the [web scraping lesson](/data-projects/web-scraping), but it was actually created for tests!

The [docs](https://playwright.dev/docs/intro) are well done. There is even a section about automatically [comparing visuals with screenshots](https://playwright.dev/docs/test-snapshots).

## Conclusion

You don't always need tests, but when you start working on a long-term or complex project, taking the time to write simple tests each time you are creating a new method or function can become time well invested.

You'll be more confident in your code and, between type checking and tests, you'll be able to avoid a lot of nasty bugs and errors! 🐞

And if you do have a bug to fix, adding a test to cover it will make sure it won't ever happen again!

Happy testing! 👷
