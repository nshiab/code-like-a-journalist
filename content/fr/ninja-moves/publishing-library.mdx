# Publier une librairie TypeScript

Avez-vous des bouts de code que vous copiez-collez constamment d’un projet à l’autre ? Si oui, il est probablement temps de créer une librairie !

Dans cette leçon, je vais vous montrer comment créer une librairie en code ouvert avec Node.js et la publier sur [npm](https://www.npmjs.com/). Nous écrirons du TypeScript, le testerons, puis le compilerons en JavaScript avec des déclarations de types pour que d’autres projets puissent l’utiliser.

Je suppose que vous avez terminé les leçons précédentes, particulièrement celles-ci :

- [Utiliser des librairies](/pushing-further/libraries)
- [Comprendre les versions de librairies](/ninja-moves/semver)
- [Utiliser des tests dans vos projets](/ninja-moves/tests)

## Créer un compte npm et un projet

npm est le registre sur lequel nous publierons notre librairie. Commencez par [créer un compte npm](https://www.npmjs.com/signup). Pour la publication manuelle présentée ici, activez l’[authentification à deux facteurs](https://docs.npmjs.com/configuring-two-factor-authentication) sur votre compte.

Notre package s’appellera `@your-username/my-first-library`. La partie avant la barre oblique s’appelle un **scope**. Remplacez `your-username` par votre nom d’utilisateur npm tout au long de cette leçon et choisissez un nom de package disponible dans votre scope.

Le générateur utilisé ailleurs dans le cours prépare des projets d’analyse de données. Ici, nous allons configurer une petite librairie autonome pour contrôler les fichiers distribués sur npm. Créez un nouveau dossier et ouvrez-le dans VS Code. Utilisez la dernière version LTS de Node.js, puis initialisez le projet dans son terminal :

```sh
npm init -y
npm install --save-dev typescript @types/node vitest
```

Dans `package.json`, indiquez `"type": "module"` pour utiliser les modules ES. Nous compléterons ce fichier dans un instant.

## Coder la librairie

Il est temps d’écrire du code ! Nous allons reprendre la fonction de la [leçon sur les tests](/ninja-moves/tests), en ajoutant un arrondi.

Créez un dossier `functions` et un fichier `getPercentage.ts` contenant le code et la documentation ci-dessous. Le commentaire au-dessus de la fonction est du **JSDoc** : les éditeurs peuvent l’afficher lorsqu’une personne utilise la fonction.

````ts showLineNumbers filename="functions/getPercentage.ts"
/**
 * Calculates a percentage, rounds it, and adds a percentage sign ("%").
 *
 * @example
 * ```ts
 * getPercentage(50, 200); // "25%"
 * getPercentage(0, 0);   // "0%"
 * ```
 *
 * @param current - The value to calculate the percentage for.
 * @param total - The total value to calculate the percentage against.
 * @returns The rounded percentage, or "0%" if total is zero.
 */
export default function getPercentage(
  current: number,
  total: number,
): string {
  if (total === 0) {
    return "0%";
  } else {
    const percentage = Math.round((current / total) * 100);
    return `${percentage}%`;
  }
}
````

Créez un fichier `index.ts` à la racine du projet. Ce sera le point d’entrée de votre librairie. Nous importons notre fonction et la réexportons avec un nom, pour permettre d’utiliser `import { getPercentage } from "..."`.

Si votre librairie grandit, vous pourrez rassembler ici ses fonctions et classes publiques.

```ts showLineNumbers filename="index.ts"
import getPercentage from "./functions/getPercentage.ts";

export { getPercentage };
```

Il est essentiel de tester votre code avant de le publier. Créez un dossier `tests` et ajoutez-y `getPercentage.test.ts`. Nous importerons depuis le point d’entrée pour tester ce que la librairie exporte.

```ts showLineNumbers filename="tests/getPercentage.test.ts"
import { test, expect } from "vitest";
import { getPercentage } from "../index.ts";

test("should return 50%", () => {
  expect(getPercentage(50, 100)).toBe("50%");
});
test("should round to 33%", () => {
  expect(getPercentage(33.333, 100)).toBe("33%");
});
test("should return 0% for a zero current value", () => {
  expect(getPercentage(0, 100)).toBe("0%");
});
test("should return 0% for a zero total", () => {
  expect(getPercentage(1, 0)).toBe("0%");
});
```

Exécutez `npx vitest run tests/getPercentage.test.ts`. Les quatre tests devraient réussir ! Nous utilisons la même syntaxe de test que dans les projets générés.

## Configurer TypeScript

Node peut exécuter notre code source TypeScript directement, mais il ne vérifie pas les types et ne compile pas notre librairie pour la distribuer. Nous utiliserons le compilateur TypeScript pour ces tâches.

Créez `tsconfig.json` pour vérifier notre librairie et ses tests :

```json showLineNumbers filename="tsconfig.json"
{
  "compilerOptions": {
    "noEmit": true,
    "target": "esnext",
    "module": "nodenext",
    "rewriteRelativeImportExtensions": true,
    "erasableSyntaxOnly": true,
    "verbatimModuleSyntax": true,
    "strict": true,
    "types": ["node"]
  },
  "include": ["index.ts", "functions/**/*.ts", "tests/**/*.ts"]
}
```

Exécutez `npx tsc --noEmit`. Cette commande vérifie notre code et les tests sans créer de fichiers de sortie.

Créez maintenant une seconde configuration pour la compilation. Elle reprend la première, active la création de fichiers et limite la compilation au code que nous voulons distribuer :

```json showLineNumbers filename="tsconfig.build.json"
{
  "extends": "./tsconfig.json",
  "compilerOptions": {
    "noEmit": false,
    "noEmitOnError": true,
    "declaration": true,
    "rootDir": ".",
    "outDir": "./dist"
  },
  "include": ["index.ts", "functions/**/*.ts"],
  "exclude": ["tests", "dist", "node_modules"]
}
```

Exécutez `npx tsc -p tsconfig.build.json`. Vous devriez voir un nouveau dossier `dist` contenant :

```text
dist/
  index.js
  index.d.ts
  functions/
    getPercentage.js
    getPercentage.d.ts
```

Les fichiers `.js` sont le code exécutable. Les fichiers `.d.ts` décrivent ses types pour les personnes qui utilisent TypeScript. Le compilateur conserve notre JSDoc dans les déclarations : les lecteurs obtiennent toujours de l’aide dans leur éditeur. Consultez le [guide TypeScript sur la publication des déclarations](https://www.typescriptlang.org/docs/handbook/declaration-files/publishing.html).

L’option [`rewriteRelativeImportExtensions`](https://www.typescriptlang.org/tsconfig/rewriteRelativeImportExtensions.html) transforme les imports relatifs `.ts` en imports `.js` dans les fichiers compilés. Ouvrez `dist/index.js` pour voir la différence !

Nous publions ce code compilé parce que Node ne retire pas les types TypeScript des packages dans `node_modules`. Des projets JavaScript peuvent aussi utiliser notre librairie sans devoir compiler notre code source.

## Préparer le package

Mettez à jour `package.json` avec les champs ci-dessous. **Conservez également la section `devDependencies` créée par npm** : ses numéros de version dépendent du moment où vous avez installé TypeScript, `@types/node` et Vitest.

```json showLineNumbers filename="package.json"
{
  "name": "@your-username/my-first-library",
  "version": "0.1.0",
  "description": "A small helper for rounded percentages",
  "type": "module",
  "license": "MIT",
  "files": ["dist"],
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js"
    }
  },
  "scripts": {
    "check": "tsc --noEmit",
    "test": "vitest run tests/getPercentage.test.ts",
    "build": "tsc -p tsconfig.build.json",
    "prepublishOnly": "npm run check && npm test && npm run build"
  }
}
```

Voici à quoi servent ces paramètres :

- `name`, `version` et `description` identifient la librairie. Consultez la [leçon SemVer](/ninja-moves/semver) pour les numéros de version.
- `license` indique la licence. Nous avons choisi [MIT](https://opensource.org/license/mit); ajoutez son texte dans un fichier `LICENSE`, avec votre nom et l’année.
- `files` limite le code publié à `dist`. npm inclut aussi certains fichiers comme `package.json`, `README.md` et `LICENSE`.
- `exports` dirige les imports vers notre point d’entrée compilé et indique les déclarations à TypeScript. Cet exemple publie un module ES.
- `scripts` fournit des commandes pratiques et exécute les vérifications, les tests et la compilation automatiquement avant `npm publish`. Consultez la [documentation du cycle de vie npm](https://docs.npmjs.com/cli/v11/using-npm/scripts).

Si `npm init` a créé un champ `"main": "index.js"`, supprimez-le : notre point d’entrée est décrit par `exports`. Si vous avez copié `"private": true` depuis un projet d’analyse, retirez-le également lorsque vous voulez publier : ce paramètre bloque la publication.

Créez `README.md` pour expliquer le package et montrer comment l’utiliser. npm affiche ce fichier sur la page du package.

````md showLineNumbers filename="README.md"
# My first library

A helper created as part of the [Code Like a Journalist](https://www.code-like-a-journalist.com/en) course.

## Installation

```sh
npm install @your-username/my-first-library
```

## Usage

```ts
import { getPercentage } from "@your-username/my-first-library";

getPercentage(50, 200); // "25%"
getPercentage(0, 0);   // "0%"
```
````

npm affiche le README, mais ne génère pas automatiquement un site de référence de l’API à partir du JSDoc. Pour une librairie plus importante, vous pouvez créer un site de documentation séparé.

Je vous encourage fortement à enregistrer le code source et les deux fichiers de configuration npm dans Git ! Consultez la [leçon sur GitHub](/git-and-github/github-basics). Ajoutez `node_modules/` et `dist/` à `.gitignore` : ils peuvent être recréés avec `npm ci` et `npm run build`.

## Vérifier le package localement

Avant de téléverser quoi que ce soit, exécutez :

```sh
npm run check
npm test
npm run build
npm pack --dry-run
```

Examinez la liste des fichiers. Elle devrait contenir le JavaScript, les déclarations, les métadonnées du package, le README et la licence. Dans cet exemple, les tests et le code source TypeScript n’ont pas besoin d’être distribués. Consultez la [documentation sur le contenu d’un package npm](https://docs.npmjs.com/cli/v11/commands/npm-publish#files-included-in-package).

Pour essayer le **véritable package** localement, exécutez `npm pack`. Cela crée une archive comme `your-username-my-first-library-0.1.0.tgz` sans la publier.

Créez un projet dans un autre dossier, initialisez-le avec `npm init -y`, indiquez `"type": "module"` dans son `package.json`, puis installez l’archive avec son chemin complet :

```sh
npm install /full/path/to/your-username-my-first-library-0.1.0.tgz
```

Créez `main.ts` avec ce code :

```ts showLineNumbers filename="main.ts"
import { getPercentage } from "@your-username/my-first-library";

const percentage = getPercentage(20, 100);
console.log(percentage);
```

Exécutez `node main.ts`. Vous devriez voir `20%` ! Nous vérifions ainsi que le point d’entrée compilé fonctionne aussi pour un projet qui utilise la librairie. Vous pouvez ajouter la configuration TypeScript habituelle ici si vous voulez vérifier les types.

## Publier la librairie

De retour dans le dossier de la librairie, exécutez `npm login` et suivez les instructions de connexion dans votre navigateur. `npm whoami` permet de vérifier le compte utilisé. Consultez la [documentation de npm login](https://docs.npmjs.com/cli/v11/commands/npm-login).

Prévisualisez la publication avec `npm publish --dry-run --access public`. Cette commande exécute les vérifications de `prepublishOnly` sans téléverser le package.

Quand vous êtes prêt à le partager publiquement, exécutez :

```sh
npm publish --access public
```

Complétez les demandes d’authentification. L’option `--access public` publie explicitement notre package avec un accès public. Ce processus manuel utilise l’authentification à deux facteurs de votre compte; le [guide de publication npm](https://docs.npmjs.com/creating-and-publishing-scoped-public-packages) explique les exigences actuelles.

Une fois la publication terminée, visitez `https://www.npmjs.com/package/@your-username/my-first-library` en utilisant votre véritable nom d’utilisateur. Votre code peut maintenant être installé par d’autres personnes, et votre README explique comment l’utiliser ! 🤩

## Publier une nouvelle version

Croyez-moi : résistez à l’envie de publier trop rapidement ! Une petite modification peut casser une librairie. Notre script `prepublishOnly` aide en exécutant les vérifications et les tests avant chaque publication.

Faisons une petite mise à jour. Ajoutez une phrase au README pour expliquer que les pourcentages sont arrondis à l’entier le plus proche, puis augmentez la version :

```sh
npm version patch --no-git-tag-version
```

Cette commande passe de `0.1.0` à `0.1.1` dans `package.json` et met à jour `package-lock.json`. Ici, `--no-git-tag-version` nous laisse gérer séparément le commit et le tag Git. Vous pourriez utiliser `minor` ou `major` pour des changements plus importants, comme expliqué dans la [leçon SemVer](/ninja-moves/semver).

Exécutez `npm publish --dry-run --access public` et examinez le résultat. Quand vous êtes prêt, exécutez à nouveau `npm publish --access public`. npm effectue nos vérifications avant de téléverser la nouvelle version ! 🥳

Une combinaison de nom et de version publiée ne peut pas être réutilisée : les corrections nécessitent donc un nouveau numéro. Votre page devrait maintenant afficher `0.1.1` et le README mis à jour.

## Mettre à jour le projet qui utilise la librairie

Dans le projet qui utilise la librairie, exécutez `npm outdated`. Regardez `Current` (version installée), `Wanted` (autorisée par `package.json`) et `Latest` (marquée `latest` sur npm).

Si `package.json` autorise `^0.1.0`, `npm update @your-username/my-first-library` peut installer `0.1.1`. Cette commande met à jour le package installé et le fichier de verrouillage en conservant la plage. Pour choisir explicitement une version et mettre à jour la dépendance, exécutez `npm install @your-username/my-first-library@0.1.1`.

Vérifiez que `node main.ts` fonctionne toujours. Dans un projet plus important, vérifiez aussi les types et les tests. Bien sûr, cette mise à jour ne changeait que la documentation, mais vous connaissez maintenant le processus complet. 🤓

## Automatiser la publication

Si vous prévoyez de mettre à jour souvent votre librairie, vous pouvez automatiser les vérifications et la publication avec GitHub Actions. Voici un processus possible :

1. Créez une issue pour un bug ou une fonctionnalité, puis travaillez sur une branche.
2. Ajoutez des tests pour le changement et ouvrez une pull request.
3. Exécutez les vérifications de types, les tests et la compilation dans GitHub Actions avant la fusion.
4. Mettez à jour la version du package et enregistrez ce changement dans Git.
5. Déclenchez un workflow de publication pour une release ou un tag Git.

Pour la dernière étape, explorez la [publication de confiance npm](https://docs.npmjs.com/trusted-publishers). Elle permet aux environnements CI pris en charge de s’authentifier sans stocker de jeton npm de longue durée. Configurez-la pour votre dépôt et votre workflow en suivant la documentation npm.

La [leçon sur GitHub](/git-and-github/github-basics) et celle sur [GitHub Actions](/git-and-github/github-actions) vous aideront. La publication manuelle est déjà un excellent point de départ !

## Packages privés

Dans une entreprise, une librairie privée peut être utile pour partager du code testé entre collègues. npm propose également des [packages privés](https://docs.npmjs.com/creating-and-publishing-private-packages), avec les conditions de compte et d’accès décrites dans sa documentation.

Un package public est accessible à tout le monde. Choisissez l’accès adapté au code que vous souhaitez partager.
