# Utiliser des tests dans vos projets

Les tests sont largement utilisés en programmation pour s’assurer que les classes, fonctions et méthodes se comportent comme prévu. Quand le code est mis à jour, les tests garantissent aussi que les changements n’ont pas touché tout le travail effectué auparavant.

Mais les tests peuvent aussi être très utiles dans les projets d’analyse de données et de visualisation. Vous pouvez les utiliser pour vous assurer que vos calculs correspondent à une référence indépendante. Ou, une fois que vous avez des résultats, pour vérifier que vos modifications n’ont pas un impact inattendu sur vos conclusions ou vos visuels.

Personnellement, j’utilise les tests pour renforcer ma confiance dans mon travail. Je peux vérifier quelque chose une fois et écrire un test pour le valider. Par la suite, je saurai avec certitude que ce résultat est garanti. Et si le test échoue, cela signifie qu’un problème sérieux s’est produit et nécessite mon attention !

Dans cette leçon, nous allons coder une fonction simple pour calculer des pourcentages et créer des tests pour nous assurer qu’elle fonctionne comme prévu.

## Configuration

Créez un nouveau dossier, ouvrez-le dans VS Code et utilisez la dernière version LTS de Node.js. Dans le terminal, exécutez `npx @nshiab/setup-data-project` et ne sélectionnez aucune librairie optionnelle. Vous obtenez la même structure et les mêmes outils que dans la [leçon d’installation](/simple-data-analysis/setup).

Nous écrirons notre script dans `sda/main.ts`. Exécutez `npm run sda` pour le lancer et le relancer automatiquement lorsque vous sauvegardez vos modifications. Utilisez `npm run all-tests` pour vérifier la mise en forme, les règles de lint, les types et les tests; `npm run fix` peut appliquer les corrections automatiques de mise en forme et de lint.

Utilisez le dossier `sda/helpers` (créez-le au besoin) et placez-y le fichier `getPercentage.ts` avec ce code. C’est la fonction que nous voulons tester. Elle s'attend à recevoir deux nombres et retourne le pourcentage sous forme de texte.


```ts showLineNumbers filename="sda/helpers/getPercentage.ts"
export default function getPercentage(
    current: number,
    total: number,
): string {
    const percentage = (current / total) * 100;
    return `${percentage}%`;
}
```

Mettez maintenant à jour `sda/main.ts` pour utiliser la fonction.


```ts showLineNumbers filename="sda/main.ts"
import getPercentage from "./helpers/getPercentage.ts";

console.log(getPercentage(50, 100));
```

La commande `npm run sda` exécute le script lorsque vous le sauvegardez.

Tout fonctionne comme prévu ! La fonction retourne `50%`.

## Créer des tests

Est-ce que notre fonction fonctionne vraiment comme prévu ? Vérifions !

Notre projet inclut déjà [Vitest](https://vitest.dev/guide/) grâce à Vite+. Nous utiliserons `test` pour décrire chaque test et `expect(...).toBe(...)` pour comparer les valeurs retournées par notre fonction avec celles que nous attendons. Il n’y a rien d’autre à installer !

Créons maintenant le fichier de test. Une bonne manière d’organiser les tests dans un projet est de garder la même structure de fichiers que le reste du code.

Ici, on pourrait créer un dossier `sda/tests` avec un fichier `getPercentage.test.ts` à l’intérieur. Remarquez que ce fichier est un fichier TypeScript classique puisqu’il se termine par `.ts`. La partie `.test` permet à Vitest de reconnaître ce fichier comme un fichier de test.

Voici ce que fait le code ci-dessous :
- `test` crée un nouveau test.
- Le premier paramètre est une description du test.
- Le second paramètre est une fonction. On y exécute ce que l’on veut tester (ici `getPercentage`) et on vérifie que le résultat est bien celui attendu avec `expect(...).toBe(...)`.
- Si le résultat est celui attendu, le test réussira. Sinon, il échouera !


```ts showLineNumbers filename="sda/tests/getPercentage.test.ts"
import { test, expect } from "vitest";
import getPercentage from "../helpers/getPercentage.ts";

test("should return 50% for 50 out of 100", () => {
  const result = getPercentage(50, 100);
  expect(result).toBe("50%");
});
```

## Exécuter les tests

Exécutez `npm run all-tests`. Cette commande vérifie la mise en forme, les règles de lint et les types TypeScript, puis exécute les tests du projet. Si une vérification de mise en forme ou de lint échoue, lancez `npm run fix`, examinez les modifications et réessayez.

<OutdatedScreenshot src="/assets/ninja-moves/tests/run-tests.png" alt={"Exécution des tests avec Deno."} lang="fr" />

Pendant que vous codez, il est pratique de relancer automatiquement un seul fichier de test lorsque ce fichier ou ses dépendances changent. Utilisez :

```sh
npx vp test sda/tests/getPercentage.test.ts --watch
```

Laissez cette commande tourner pour le reste de la leçon. Appuyez sur `CTRL` + `C` pour l’arrêter. Cette commande exécute les tests; `npm run all-tests` exécute aussi les autres vérifications du projet, donc utilisez-la à nouveau avant de terminer vos modifications.

La [documentation de Vitest](https://vitest.dev/guide/) présente d’autres options.

## Ajouter des tests

Selon votre contexte, le test que nous venons d’écrire peut être suffisant. Par exemple, peut-être que vous vouliez simplement vérifier le résultat d’une étape dans votre analyse de données et que vous voulez que cela reste comme ça à l’avenir.

Mais pour les besoins de cette leçon, ajoutons quelques tests supplémentaires. Testons des cas limites.

Par exemple, que doit-il se passer si le premier nombre est `0` ? Et si le second est `0` ? Peut-être que nous voulons que notre fonction retourne `0%` dans les deux cas.

Modifiez le fichier avec le code ci-dessous. Dès que vous enregistrerez le fichier modifié, les tests se relanceront automatiquement.


```ts showLineNumbers filename="sda/tests/getPercentage.test.ts" {9-17}
import { test, expect } from "vitest";
import getPercentage from "../helpers/getPercentage.ts";

test("should return 50% for 50 out of 100", () => {
  const result = getPercentage(50, 100);
  expect(result).toBe("50%");
});

test("should return 0% for 0 out of 100", () => {
  const result = getPercentage(0, 100);
  expect(result).toBe("0%");
});

test("should return 0% for 1 out of 0", () => {
  const result = getPercentage(1, 0);
  expect(result).toBe("0%");
});
```
<OutdatedScreenshot src="/assets/ninja-moves/tests/fail.png" alt={"Un test a échoué."} lang="fr" />

On peut voir que le deuxième test est passé, mais que le troisième a échoué !

Quand `total` vaut `0`, notre fonction retourne `Infinity%` au lieu de ce que nous voulons, c’est-à-dire `0%`.

Mettons à jour notre fichier `getPercentage.ts` pour corriger cela. Modifiez le fichier avec le code ci-dessous. Dès que vous enregistrerez le fichier, les tests se relanceront automatiquement.


```ts showLineNumbers filename="sda/helpers/getPercentage.ts" {5-7, 10}
export default function getPercentage(
  current: number,
  total: number,
): string {
  if (total === 0) {
    return "0%";
  } else {
    const percentage = (current / total) * 100;
    return `${percentage}%`;
  }
}
```

Et maintenant, on peut voir que le troisième test est passé.

On sait aussi que le comportement précédent est toujours là puisque les deux premiers tests sont également passés !

<OutdatedScreenshot src="/assets/ninja-moves/tests/all-passed.png" alt={"Tous les tests sont passés."} lang="fr" />

## Tests automatisés

Vous pouvez bien sûr toujours lancer les tests localement. Vous pouvez même créer une [tâche](/pushing-further/tasks) pour les exécuter plus facilement.

Mais si vous utilisez GitHub, vous pouvez configurer des tests automatisés dans vos projets. C’est une configuration courante pour les librairies en code ouvert, mais vous pouvez l’utiliser pour n’importe quel projet.

Par exemple, j’ai des centaines de tests en place pour la [librairie Simple Data Analysis](https://github.com/nshiab/simple-data-analysis). Vous pouvez [les explorer ici](https://github.com/nshiab/simple-data-analysis/tree/main/test/unit/methods).

J’utilise GitHub Actions (consultez [la leçon à ce sujet](/git-and-github/github-actions)) pour les déclencher automatiquement lorsqu’une *pull request* est ouverte ou mise à jour vers la branche `main`.

La *pull request* indique si les tests ont réussi. Si un ou plusieurs échouent, il faut continuer à travailler avant de fusionner. Les règles du dépôt peuvent aussi exiger la réussite de ces vérifications et bloquer le bouton de fusion tant que ce n’est pas le cas. Vous pouvez consulter [le *workflow* ici](https://github.com/nshiab/simple-data-analysis/blob/main/.github/workflows/all-tests.yml).

Ce ne sont que quelques lignes de code, mais cela garantit que la librairie fonctionne comme prévu. Et ça m’a évité plusieurs fois de publier une nouvelle version cassée de la librairie ! 😇

## Tester des visualisations

Les tests sont faciles à mettre en place lorsque votre code **retourne** quelque chose comme un texte, un nombre, une date, une liste ou un objet.

Mais vous pouvez aussi utiliser des tests pour comparer des éléments d’une page web, comme des graphiques, et plus encore, avec [Playwright](https://playwright.dev/). Nous avons utilisé Playwright dans la [leçon sur le web scraping](/data-projects/web-scraping), mais à la base, il a été créé pour faire des tests !

La [documentation](https://playwright.dev/docs/intro) est très bien faite. Il y a même une section sur la [comparaison automatique de visuels avec des captures d’écran](https://playwright.dev/docs/test-snapshots).

## Conclusion

Vous n’avez pas toujours besoin de tests, mais dès que vous travaillez sur un projet à long terme ou complexe, prendre le temps d’écrire de simples tests à chaque fois que vous créez une nouvelle méthode ou fonction peut s’avérer être un excellent investissement.

Vous aurez plus confiance en votre code et, entre le typage et les tests, vous éviterez beaucoup de vilains bugs et erreurs ! 🐞

Et si jamais vous avez un bug à corriger, ajouter un test pour le couvrir garantira qu’il ne reviendra jamais !

Bonnes séances de test ! 👷
